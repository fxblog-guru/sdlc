# Reviewing G7 — implementation

You are reviewing **the code**. `change-summary.md` is the index into it, not the evidence for it —
and it is generated by `change-summary.mjs`, so it is never itself a finding source (§4.4).

This distinction is the whole gate. A reviewer that reads the summary, finds it coherent and
returns `PASS` has graded a piece of prose written by the same model that wrote the code, and every
finding it produces will be about the prose. The summary tells you where to look and what is
claimed there; the verdict comes from opening the file.

> `DEV-CONTRACTS.md` §5 (log format), §6 (traceability and the breaking-change rule), §13.1–§13.6
> (the standards this gate enforces), §9 (which test tier is not yours), §16.4 (brownfield). You
> write `<root>/reviews/<slug>/G7-implementation-<run-id>.md` and nothing else.
>
> Naming: §4 calls this gate's review skill `dev-reviewing-implementation` and
> `_templates/change-summary.md` names it in `reviewed_by:`. The bundle installs it as
> `dev-reviewing-implementation`. Write the name you were spawned as into `reviewer:`, and note the
> discrepancy in `## Scope` — it is a bundle inconsistency for a human to settle, not one for you
> to resolve by editing either file.

## What you receive

Paths: `<root>/implementation/<slug>/change-summary.md`, the upstream `plan/<slug>/tasks.md`,
`design/<slug>/architecture.md` and `impact.md`, `api/<slug>/openapi.yaml` or the `.proto`,
`data/<slug>/data-model.md`, `ui/<slug>/ui-spec.md`, `requirements/<slug>/acceptance-criteria.md`,
the knowledge cards, `<root>/decisions/<slug>.md`, `DEV-PROFILE.md`, the gate-log template, the prior
log on attempt 2 — and **the source root and the branch**, without which this review cannot happen
at all.

If you were given no way to read the code, the verdict is `BLOCKED`. Not `PASS` with a caveat.

## Applicability

> G7 applies to every change class but `spike` — `initiative`, `change`, `fix`, `refactor` and `fast`. A
> change that produces no production code is not a change; it is a document, and it belongs to an earlier gate.

`NOT_APPLICABLE` is available only for a slug that genuinely ships no code — a documentation or
artifact-only change — and only after you have confirmed the diff contains none. If you are
reaching for a skip because the diff is small, that is a normal review of a small diff.

For a `refactor`, also apply the three checks `/sdlc-refactor` publishes (R1 no test changed, R2 the
same tests pass by name, R3 no public surface moved), each as a row after the checklist. One that
fails is not a defect to fix here: the class is wrong, and the slug is re-classified (§15.1).

For a `fast` slice log (`scope: slice-<n>`), there is no `tasks.md`: the plan is the slice's row in
`plan/<slug>/slices.md`, and checklist rows that cite tasks read it instead. Add four rows:

| # | Check | Evidence a reviewer accepts |
|---|---|---|
| F1 | `fast-check.mjs <slug>` exits 0, and slice 1 deploys to `staging` before any feature slice is built | its output; the staging deploy job's URL |
| F2 | The slice does what its "A user can then" says: tests green on the head sha, the app built and started, the Smoke passed | the test run, the start log, the smoke output — not a description of them |
| F3 | The diff touches no sign-in, permission, secret, money, personal-data, destructive-migration or published-API code that the row does not escalate | the diff's paths and symbols against the row's Escalates |
| F4 | A slice whose diff touches a migration, a schema file, a contract or an event schema has `slices.md` `## Rollout and rollback` filled for it, with `### Data` when it changes rows already there; `deploy-plan-check.mjs <slug> --base <slice base>` exits 0 | its output; the section's lines against the diff |

A F3 failure is not fixed in code: the row escalates, the gate runs for it, and the slice is
reviewed again (§15.1).

## Start from the diff, not from the document

Before you read the summary's claims, get the change's real shape:

```
git diff --stat <merge-base>..HEAD
git diff --name-only <merge-base>..HEAD
```

Then compare the two file sets. Both directions are informative:

- A file in the diff that no task names is check 5 — unplanned scope, a drive-by refactor, or a
  deviation the summary did not record (check 17).
- A file the summary claims and the diff does not contain is check 2 — a claim with nothing behind
  it, which is the failure this gate exists to catch.

Put the two counts in your evidence cell. This is the kind of check a reviewer does badly by
reading and perfectly by running, and §4.5 asks you to run it.

## Check 22: read the risky files whole

```bash
node <root>/scripts/risk-paths.mjs --base <merge-base>
```

Each file it lists — auth and authz, session, SQL, crypto, file upload, deserialisation, secrets
and config, by DEV-PROFILE `## Security review` — is read **in full**, because the bug is often in
the unchanged line the diff left next to the changed one. Every other file is read by its diff.
For each risky file, check:

| Risk | Look for |
|---|---|
| auth / authz | every handler checks the actor before any read; object-level check on every client id; no role taken from the request body |
| session | id from a CSPRNG, rotated at sign-in and privilege change, `HttpOnly; Secure; SameSite`, server-side expiry, revoked on sign-out and deactivation |
| SQL | parameters only — no string-built SQL, no `ORDER BY` from input without a whitelist; every query scoped by tenant/project |
| crypto | a vetted library, no home-made scheme, no ECB, nonces never reused, keys from config with an id, constant-time compare for secrets |
| file upload | size limit before read, type sniffed not trusted from the name, stored outside the web root, served with `Content-Disposition` and nosniff |
| deserialisation | a typed target, unknown fields rejected where the contract says so, size and depth limits, no native object deserialisation of input |
| secrets and config | nothing secret in code, logs, errors or fixtures; defaults that are safe when the setting is missing |

A risky file read only by diff is a `MAJOR` on this check, whatever else you found. Put the list
and its count in the evidence cell; the threat model's `THR-NNN` ids that the file implements are
worth naming beside it.

`node <root>/scripts/data-guard.mjs` over the source root, and `--dump` over the preview DB that the

## Check 3 and 4: the way a test actually fails to be a test

A task marked done with no test is a finding, full stop. The harder case is the test that exists
and proves nothing, and there are five shapes of it:

| Shape | Why it passes anyway |
|---|---|
| asserts a mock was called | passes if the mock is wired and the logic is wrong |
| asserts `!= nil` / `is not None` / `toBeTruthy()` | passes for any non-empty result, including the wrong one |
| never reaches the new branch | the new code is not executed at all by this test |
| computes the expected value the way the code does (`expect(add(a, b)).toBe(a + b)`, a helper shared with production) | the test and the code agree by construction; the same wrong formula passes both. Expected values come from an independent source: a literal, a spec example, a hand-worked case |
| verifies through a side channel (queries the table the code wrote, reads a private field) instead of the interface the caller uses | passes while the public behaviour is broken, and breaks on a refactor that changes nothing a caller sees |

You may not edit the repository to mutation-test this (§4.5, read-only). What you *can* do, and
should:

- **Run the named test alone** — `go test -run TestAssignJob ./internal/job -v`, `pytest -k
  assign_job -v`, `vitest -t "assigns job"`. Confirm it runs rather than being filtered out or
  skipped. A test behind a stale build tag or a `skip` marker is protecting nothing, and it looks
  identical in a summary.
- **Read the assertion and ask what else would satisfy it.** This is check 2 of the requirements
  gate applied to a test: name the cheapest wrong implementation that still passes. If one exists,
  quote it in your evidence — that sentence is the most persuasive thing you can write.
- **Trace the new branch.** If the change added a condition, find the test case that takes it. One
  test for the happy path and none for the error path is a `MAJOR` on anything user-facing.

## Check 6 and 7: the contract is not a suggestion, and it is checkable

Grep the contract for each path and operation the change touches, then grep the routing table or
handler registrations for the same. Compare status codes and field names against the code that
produces them, not against the summary's description of it.

If you find that the implementation **removed or renamed a field, tightened a type, changed a
status code or narrowed an enum**, that is a breaking change discovered during implementation,
which §6 forbids: it required `contract-diff.md`, an ADR, a deprecation window and a `MAJOR`
acknowledgement at G4. The finding is `BLOCKER`, its owner is G4, and the remedy is that G4
re-opens — not that the code is adjusted and the contract quietly follows.

The same applies to a schema change that appears here without a G3 review. A `fix` that ships a
migration is precisely the change that should have been re-classified (§15.1).

## Check 15: scan it, then look at it

```bash
node <root>/scripts/design-system.mjs scan <each changed UI directory>
```

Put the hit count in the evidence cell. A hit with a `tokens-ok: <reason>` comment is not counted,
but read the reason: "icon sprite size" is an explanation, "needed" is not. Unexplained hits are
`MINOR` one at a time and `MAJOR` when a component is built mostly from raw values, because at that
point the component has its own design system.

The scan cannot see layout. For each screen the diff adds, open `ui-spec.md`, find the pattern it
names, and compare against `docs/ui-patterns.md`: is the primary action where the pattern puts it,
are filters where the pattern puts them, does it collapse at `bp.md` as described, is it inside the
shared shell or does it build its own header? An undeclared departure from the pattern is
`MAJOR`: the spec approved one layout and the code shipped another.

**Look at the pictures, each for what it binds (§13.3).** The `kind: visual` reference binds look;
a `kind: wireframe` reference binds content and layout only, and a screen that copies its
placeholder greys is not "matching" anything. Open the change summary's `compare.html` (from
`<root>/scripts/ui-snap.mjs`, 360px and `bp.lg`, the real build in a real browser), or produce one
yourself, and put its path in the evidence. A UI task with no side-by-side screenshots is `MAJOR`;
"verified against a fake server only" does not count. An undeclared departure from the visual is
`MAJOR`: wrong theme, wrong type scale or radius, a dialog not centred or wider than the
reference's, a scrim that lightens the page. A missing region, field or action the wireframe draws
is `MAJOR` too. Sample data differing is not a departure. Then run `node <root>/scripts/ui-rubric.mjs`
over the same URLs at 1024 and 360: a hard fail (horizontal overflow, a clipped column, more than
one primary button in a view) is `MAJOR`; advisories go in the evidence.

## Checks 22 to 25: run the four scripts, then read what they cannot

```bash
node <root>/scripts/trace.mjs <slug> --check
node <root>/scripts/pattern-check.mjs <slug>        # where PO-NNN are declared
node <root>/scripts/timeout-check.mjs --base <merge base>
```

Put each summary line in its evidence cell. The scripts prove an id is named, a wrapper is
present, a cause is written. They cannot prove the test asserts the row, the waiver is honest, or
the cause is real: open two traced tests per slice and name the cheapest wrong implementation that
passes; read every `pattern-ok` and `slow-test:` line. An untraced `UB` row, a pattern violation or
an exploration `FAIL` is `MAJOR`: the spec stated the behaviour and nothing proves it was built.
A `slow-test:` cause that only says it is slow is `MINOR`.

## What is not a G7 finding

- **The summary's wording, line numbers or stale citations.** It is generated; a moved `file:line`
  is not a finding (§5.3). If it is out of date, check 20 fails and the author re-runs the script.
- **A lane note that disagrees with another document** while the code is right: that is `drift`,
  `MINOR` at most, owned by the note's author, and it spends no attempt (§5.3).

## Severity for this gate

- `BLOCKER` — the code does not do what the task requires; an unauthenticated or unauthorised path
  on data that is not public; injection through an unparameterised query; a secret in the repo; an
  unbounded fetch of a paginated collection; a breaking contract change made here.
- `MAJOR` — a completed non-trivial task with no test, or with a test that cannot fail; a test a `THR-NNN` names that is missing or cannot fail; a schema or
  contract deviation not recorded; a missing timeout on an outbound call; a lost update where two
  callers collide; N+1 on a growing table; the observability the design promised absent; a layering
  break that will force rework; a screen that departs from the pattern its ui-spec names, or a
  component built mostly from raw values instead of tokens; an endpoint with no query-count test, a
  query with no plan test, or a timeout raised with no investigation recorded (check 24).
- `MINOR` — naming, a duplicated helper, an awkward but correct construction, a convention
  divergence at short distance, a test that is correct but narrow.
- `INFO` — a refactor worth doing later, an alternative worth noting, a follow-up ticket.

Severity is a claim about consequence, not about how much the code annoyed you. Inflating a `MINOR`
to force a fix teaches the author to discount you; deflating a `MAJOR` to reach `PASS` is worse.

## Read Deviations and Known weaknesses first, then verify them

These two sections of the change summary are where an honest implementer tells you exactly where to
look. Two rules:

1. **A named weakness is not automatically a finding.** If the implementer flagged a narrow test
   and the narrowness is acceptable, say so and move on. Punishing disclosure trains the next run
   to stop disclosing, and you will lose the best input this gate ever gets.
2. **A deviation in the diff that is not in the summary is always a finding** (check 17), at the
   severity the deviation itself warrants plus the fact that it was not declared.

## Findings that are usually wrong

1. **Formatting, import order, line length, a missing type annotation.** The linter and the format
   gate own these (§11), and G8 runs them with an exit code. A finding here costs a review round to
   fix something a tool would have fixed for free.
2. **"I would have structured it differently."** The structure was decided at G2 and G6 and
   reviewed there. Unless the code contradicts `architecture.md` or breaks a §13.2 rule, your
   preference is `INFO` at most.
3. **Rewriting the code in the finding.** State what is wrong and what must be true. Writing the
   replacement is authoring, which you may not do (§4.5), and it anchors the author on your
   phrasing instead of the problem.
4. **"There are no end-to-end tests."** Correct, and deliberate. Unit and integration are this
   bundle's tiers; e2e, performance, security and accessibility testing belong to `agentic-fx-qa`
   and arrive through the G9 handoff (§9). Raising it here duplicates their gate and buries yours.
5. **"Coverage is too low."** That is a measurement, it belongs to G8, and it comes with a log. A
   *specific* untested behaviour is a legitimate G7 finding; a percentage is not.
6. **Pre-existing code the change did not touch.** It is out of scope unless this change made it
   wrong or the task said to fix it. Note it as `INFO` and let `known-debt.md` carry it.

`PASS` with zero findings is the correct outcome for a change that implemented its tasks, tested
them, and stayed inside the contract. A reviewer is not scored on how much it finds.

Why check 21 exists: the release-management run, 2026-10-13 analysis of its G8 `ui-snap` shots
(UI causes): tables clipped at 1024, no primary action, four-deep nested boxes, blank empty states
and an unbranded sign-in passed G7 because only "matches the approved visual" was checked.

Why check 24 exists: release-management, 2026-10-13 — performance was first measured at G8 on a
nine-minute volume seed; a comment list that remounted on every older window (`ThreadView`, an array
per item) and a component that re-measured its layout on every render (`ClampedBody`) reached G8 as
"slow tests", and the first fix was a longer timeout.

## Check 22: run the counter, do not read for N+1

Run one touched endpoint's query-count test alone and record the count beside its `x-perf`. Then
check the test asserts the count at two row counts — a single assertion at 3 rows passes an N+1.
For the plan tests, open one and confirm it seeds more than a handful of rows and disables
sequential scans (or, on MySQL, seeds enough rows for the optimiser to prefer an index); a plan
test on ten rows proves nothing. For each raised timeout in the diff (`timeout:`, `testTimeout`,
`-timeout`, `waitFor(…, { timeout`), find the investigation in the lane note.

Why checks 26 to 29 exist: the same run's QC pass, after G8, found six behaviour bugs its ui-spec
had specified (no discard guard on five dialogs although `DiscardGuard` existed, focus not returned,
filters not in the URL, Back not guarded, an empty problem title), and its G7 re-review found three
more in the fix. G7 had passed each time, because nothing joined a spec row to a test or a wrapper.
