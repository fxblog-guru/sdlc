# Blueprint: web-api-ts

A TypeScript product split into two deployables in one repository: a web app that renders the UI and
an API service that owns the domain, the database and the jobs. The web app reaches the API only
over the HTTP contract G4 approved, through a client generated from it. Pick this when the client
and the server should ship, scale or move host independently, or when the owner asked for them
apart (the `Shape:` decision, §18.7). One Next.js process with its server code inside is `nextjs`.

## Standards it follows

| Area | Standard | What it decides here |
|---|---|---|
| Workspaces | [npm workspaces](https://docs.npmjs.com/cli/using-npm/workspaces) or [pnpm workspaces](https://pnpm.io/workspaces) | `apps/*` and `packages/*` are packages named `@<product>/web`, `@<product>/api`, `@<product>/contract` |
| Contract | [OpenAPI 3.1](https://spec.openapis.org/oas/v3.1.0), types and client generated by [openapi-typescript](https://openapi-ts.dev/) | `packages/contract/openapi.yaml` is the G4 contract; `src/generated/` is built from it and never edited |
| Web | [Next.js project structure](https://nextjs.org/docs/app/getting-started/project-structure), [bulletproof-react](https://github.com/alan2207/bulletproof-react/blob/master/docs/project-structure.md) | `src/app/` routes only; `src/features/<feature>/` owns its components and its calls through the contract client |
| API | [Ports and adapters](https://alistair.cockburn.us/hexagonal-architecture/) | `src/<domain>/{domain,app,adapters/{db,http}}/`; HTTP handlers are adapters; nothing imports React |
| Images | [Dockerfile best practices](https://docs.docker.com/build/building/best-practices/) | one multi-stage `Dockerfile` per app, two images: `<product>-web` and `<product>-api` |
| Deploy | the skeleton pipeline (`<root>/_templates/skeleton/.gitlab-ci.yml`) | both images built, pushed with the commit SHA, deployed to `staging` on merge and to `production` on approval |
| Shared parts | `README.md` §What every blueprint shares | — |

## The tree

```
.
├── apps/
│   ├── web/                       UI only — image <product>-web
│   │   ├── src/app/               routes: read params, call a feature, render
│   │   ├── src/features/<feature>/{components,hooks}/  api.ts   calls the API through @<product>/contract
│   │   ├── src/components/{ui,layouts}/  src/lib/  src/styles/
│   │   └── Dockerfile  package.json  next.config.ts
│   └── api/                       the domain — image <product>-api
│       ├── src/<domain>/{domain,app,adapters/{db,http}}/
│       ├── src/platform/{errors,config,db,obs,auth}/   errors is the one RFC 9457 mapper
│       ├── src/jobs/              scheduled and queued work; runs in the api image
│       ├── src/server.ts          wiring: routes, adapters, the port
│       ├── migrations/
│       └── Dockerfile  package.json
├── packages/
│   └── contract/                  openapi.yaml (the G4 contract) → src/generated/ (types + typed client); no hand-written logic
├── tests/{integration,e2e,contract,perf,fixtures}/
├── deploy/compose/                compose.yaml for the local stack (web, api, database)
├── ops/                           deploy.sh  compose.prod.yaml  runbooks/  observability/
├── scripts/  docs/  dev/  ci/
├── README.md  CONTRIBUTING.md  Makefile|Taskfile.yml  .editorconfig  .env.example  CODEOWNERS
└── package.json (workspaces)  tsconfig.base.json  eslint.config.mjs
```

## Rules beyond the shared ones

1. `apps/web/**` never imports `apps/api/**`, the `@<product>/api` package, or a database driver.
   It reaches the server only through `packages/contract` over HTTP. This is the split the owner
   chose; one import across it makes the two deployables one again.
2. `apps/api/**` never imports `apps/web/**`, React or Next.js.
3. `packages/contract/**` imports neither app. It is generated; the contract test in
   `tests/contract/` holds the running API to it.
4. Inside the API, `domain` imports no layer above it; inside the web app, features never import
   each other.
5. Each app has its own `Dockerfile` and image, and the pipeline deploys both at one SHA. A
   migration runs from the API image before the API starts (§7).

`*/api` and `*/web` match both a path inside the app (`apps/api/…`, resolved from a relative
import or an alias) and the workspace package (`@<product>/api`).
